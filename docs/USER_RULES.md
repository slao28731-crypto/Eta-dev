# 与用户协作的规则（最高优先级）

> 本文件记录**用户对 Agent 工作方式的硬性要求**。
> 优先级高于其他文档：任何流程与本文冲突，以本文为准。
> 每次接到需求前必读。

---

## 规则一：先摸清链路，再反向提问，最后才动代码

用户提出需求后，**禁止直接改代码**。必须按下面顺序走：

### 第 1 步：定位完整逻辑链

不用 grep 猜，用图谱 + 精读，把这条链走通：

```bash
# 1. 找到入口
graphify query "<需求关键词>" --budget 3000

# 2. 看涉及的类连了谁
graphify explain "<类名>"

# 3. 看改动的影响面
graphify affected "<类名>" --depth 2
```

然后**实际读代码**，把链路走完整：

```
用户操作 → UI 层 → ViewModel/State → Runtime → 工具/Provider → 数据层 → 落盘
```

要能回答出：
- 这个功能从哪进（哪个入口）
- 经过哪几层、哪几个类
- 状态存在哪（内存 / Room / DataStore）
- 出错时怎么表现
- 有没有跨进程（Hook 侧）
- 谁是 God Node（改了会连带炸）

**如果链路没走通，不许提方案。**

### 第 2 步：反向思维提问

摸清链路后，**不要顺着用户的话往下做**。要么问清楚的，要么指出问题。

必须覆盖的提问维度：

| 维度 | 问什么 |
|---|---|
| **真实目的** | 你要的是「看起来像这样」还是「实际能那样」？为什么要这个？ |
| **使用场景** | 什么情况下会用到？多久用一次？谁用？ |
| **边界** | 极端情况怎么办？网络断了？权限没了？数据是空的？ |
| **冲突** | 这和你说的另一件事有没有矛盾？ |
| **代价** | 这个改法要动 5 个文件，有没有更小的路？ |
| **替代** | 换个思路能不能达到同样效果、但改动量只有 1/3？ |
| **取舍** | A 方案快但难维护，B 方案慢但干净，你选哪个？ |
| **可验证** | 改完你怎么判断它成了？能截图吗？能看日志吗？ |

### 第 3 步：确认后才动代码

提问完，把**你的理解复述一遍**，让用户确认：

```
我理解你要的是：______
关键约束是：______
我打算这样改：______（涉及 N 个文件）
不改的部分：______
```

用户点头了才动手。**没点头不许改。**

### 为什么这么要求

用户在上一轮对话里已经踩过一次：需求说得简单，Agent 直接开干，结果做出来的不是想要的东西，返工。
**问 5 分钟，省 2 小时返工。**

## 规则二：用户说的是人话，Agent 要负责翻译

### 用户怎么说话

用户**不会用专业术语**，也不会写精确的提示词。他说的可能是：

| 用户说 | 真实含义 |
|---|---|
| 「这里不好看」 | 可能是配色、间距、字体、布局中的任意一种，或多种 |
| 「太慢了」 | 可能是启动慢、响应慢、渲染卡、网络慢，要问清 |
| 「加个功能」 | 功能是什么、放哪、给谁用、什么条件下触发，全都没说 |
| 「跟那个一样」 | 哪个？要具体指认 |
| 「弄一下」 | 要问弄什么、弄成什么样 |
| 「有问题」 | 什么问题？什么时候出现？有截图吗？ |

### Agent 要做什么

**1. 不要装懂**

听不懂就问。装作懂了然后做错，比问三句更糟。

**2. 用具体选项代替开放提问**

❌ 差：「你想要什么样的效果？」（用户答不出来）
✅ 好：「三种做法：A 快但粗糙，B 慢但精致，C 折中。你要哪个？」

**3. 把技术选择翻译成用户能感知的结果**

❌ 差：「我打算用 Flow 替换 LiveData，用 StateFlow 承载 UiState」
✅ 好：「改完之后，界面状态变化不会再闪一下，触摸响应会跟手一些」

**4. 主动指出用户没想到的坑**

用户说「加个悬浮按钮」，你要说：
「加了之后会在某些页面挡住内容，而且部分 ROM 需要额外悬浮窗权限，可能第一次不生效。要不要改成可拖拽、可关闭的？」

**5. 不确定就先给最小可验证版本**

用户说不清楚时，别憋大方案。先给能跑的最小版，让他看到实物再调。

**6. 一次只问 3~5 个问题**

别一口气抛 20 个问题。挑最关键的，问完再往下走。

## 规则三：改动必须可回滚

用户会做实验，也会有「这个功能我不要了」的时候。**每个改动都要留下退路。**

### 分层看待「回滚」

| 层级 | 能否回滚 | 关键点 |
|---|---|---|
| **代码** | ✅ 随便回 | git 里永远有历史 |
| **App 数据**（聊天记录/配置/角色卡/记忆） | ❌ **改了就回不去** | 必须提前备份 |
| **数据库结构**（Room `version`，当前 22） | ⚠️ **只能升不能降** | 装旧版会崩 |

### 改数据库之前，必须先警告用户

涉及以下任何一项，**动手前必须明确告知风险并要求用户备份**：

- 改 `EtaDatabase` 的 `version`
- 新增 / 删除 Entity
- 改 Entity 的字段名或类型
- 加 / 删表、加 / 删索引

告知模板：

```
⚠️ 这次改动会修改数据库结构（version 22 → 23）。

后果：装回旧版 App 会直接崩溃，数据无法恢复。
必须做的：先在 App 里导出数据，或者跑 `bash scripts/backup-app-data.sh`。

确认已经备份，我再开始改。
```

### 什么时候必须先备份

| 情况 | 要不要备份 |
|---|---|
| 只改 UI | 不用 |
| 只加工具 / 改 Provider | 不用 |
| 改 hook 逻辑 | 不用 |
| **改 Room schema** | **必须** |
| **改数据序列化格式**（transcript / MEMORY.md 结构） | **必须** |
| **改 DataStore 的 key 或结构** | **必须** |

### 回滚操作规范

**优先用 `git revert`，不要用 `git reset --hard`。**

理由：`revert` 会生成一个「撤销某次改动」的新提交，历史完整保留，以后想再要回来也方便。`reset --hard` 会丢历史。

```bash
# 推荐：反向提交
git revert <commit>

# 只是暂时切回去看，不动历史
git checkout <commit> -- <某个文件>

# 危险：丢历史，只在确认没别人依赖时用
git reset --hard <commit>
```

**不要 `git push --force`**，除非用户明确要求。

### 可用还原点

| 类型 | 位置 |
|---|---|
| 基线 tag | `v0.0.1-baseline`（已推送远端） |
| 提交历史 | `git log --oneline` |
| App 数据备份 | `/sdcard/eta-backup/<时间戳>/`（跑 `scripts/backup-app-data.sh` 生成） |

### 实验性改动走分支

大改动 / 不确定的改动，先开分支：

```bash
git checkout -b feature/xxx    # 从当前状态开分支
# 改、测
git checkout clean && git merge feature/xxx    # 满意了合回来
git branch -D feature/xxx      # 不满意直接扔，主分支没动过
```

**主分支 `clean` 永远保持可用**。

## 规则四：回答风格

- **结论先行**，不要铺垫
- **说人话**，术语出现就必须解释
- 需要选择时**给明确推荐**，不要列一堆让用户自己挑
- 不确定的地方**直说不知道**，不编
- 出错了**先认**，再给修法

---

## 检查清单（每次接需求先过一遍）

```
【动手前】
□ 我用 graphify 定位了完整链路吗？
□ 我实际读过相关代码吗？
□ 我知道改动的 God Node 影响面吗？
□ 我向用户提问了吗？（至少 3 个）
□ 我复述了理解并得到确认吗？
□ 我指出了用户可能没想到的坑吗？
□ 我给了明确推荐，而不是让用户自己挑吗？

【如果碰数据库/序列化/DataStore】
□ 我明确警告了「装回旧版会崩」吗？
□ 用户已经备份了吗？（scripts/backup-app-data.sh）
□ 我写了 Migration 而不是 destructive 吗？

【收工】
□ 我说清楚这次改了什么、怎么回滚吗？
```

**任何一项没打勾，就不许动代码。**

## 提问模板（直接套用）

摸清链路后，用这个结构回复用户。**不要问开放式问题，给选项。**

```markdown
## 我摸到的链路

你要改的应该是这里：

```
<入口> → <类 A> → <类 B> → <落盘/发出>
```

涉及 `N` 个文件，其中 `XXX` 是枢纽（`M` 条依赖），改它会连带影响：<列表>

## 我不确定的三点

**1. 你要的效果是哪种？**

| 选项 | 效果 | 改动量 |
|---|---|---|
| A | <具体描述> | 1 个文件 |
| B | <具体描述> | 3 个文件 |
| C | <具体描述> | 5 个文件 |

我推荐 **B**：<理由>

**2. 这种情况怎么处理？**

当 <边界条件> 时，应该：① 报错提示 ② 静默降级 ③ 弹窗询问？

我推荐 **①**：<理由>

**3. 这会带来一个副作用，你能接受吗？**

<具体说明>。

如果不能接受，替代方案是 <方案>，代价是 <代价>。

## 我的理解

- 你要的是：<一句话>
- 不改的部分：<列表>
- 预计涉及：<N> 个文件，<M> 行改动

**确认后我就开始，或者告诉我哪里理解错了。**
```

### 什么时候可以跳过提问

只有三种情况：

1. **纯文字/文档改动**（改 README、改注释）
2. **用户明确说了「你直接做，不用问」**
3. **缺陷修复且根因唯一确定**（比如控制台报了个明确的错，只有一种修法）

其他所有情况，**必须提问**。
